ROP 链路分析

讲解rop：
由于这是mips他需要sleep(1)，再shellcode

这个exp使用4个garget，中间借用t9作为间接跳转
1.0x57E50

如果使用move $a1,0x1
给a1传值会导致，cookie的环境变量截断，因为0x1在内存是0x0000000000000001，其中的\x00会截断cookie

所以使用，libc中的garget端给a1传值，并将

作为下一跳板

2.0x436D0

使用这个作为第二跳板的原因是，他在给t9传s3(sleep地址)后
又使用栈上sp+4的偏移给ra赋值，并控制s1-s4用于后续值的传递

这直接控制了sleep函数返回后的地址
因为正规函数返回地址使用ra寄存器

sleep 返回后会跳到用于设置 a1 的 gadget。

3.0x3B974

将栈上sp+0x18的位置，赋值给了a1,使得a1指向构造的shellcode

随后通过将 t9 指向 a1 的 gadget 跳入 shellcode。

4.0x37E6C

将执行流劫持到a1(即我们构造的shellcode)

QEMU-user + GDB 调试版 exp

这是你原先那份 exp_gdb.py：QEMU 的 -g 1234 等待 GDB remote，body 写入 stdin，interactive() 留住进程终端。它用于观察控制流；到 shellcode 的 execve 后，QEMU gdbstub 断开是预期行为。此脚本使用 QEMU-user 的 libc base 0x2b300000。运行目录需按脚本注释放置为 rootfs/htdocs/exp_gdb.py，并准备对应 b09 rootfs。

ROP gadget 思路来自公开的看雪文章。这份调试版 exp 的完整代码如下（也可单独下载）。注意：qemu-mipsel -L rootfs 设置的是 ELF interpreter prefix，不等于 chroot；execve 后 gdbstub 断开是调试连接结束，不表示已得到隔离的 guest shell。

隔离 QEMU-user ROP + shellcode 复现

下面给出独立的本地复现 runner。它校验 b09 rootfs 的版本和哈希，创建临时 rootfs 副本，并通过 bwrap --unshare-user --unshare-net 在私有网络命名空间运行 QEMU-user；不会访问真实设备或外网。gadget 链思路来自看雪公开文章；shellcode、隔离 staging 与 guest-shell 判据适配本地实验。此直接 CGI harness 不等同于原厂 httpd 的完整 HTTP 请求链。

复现结果与版本边界

QEMU-user + GDB 调试 exp 与 bwrap 隔离 runner 是两种用途不同的脚本：前者供单步观察 QEMU guest 控制流；后者用私有 user/network namespace 验证 MIPS guest shell，不能混称。隔离 runner 的输出证明 b09 guest shell 已启动；这两份脚本均绕过原厂 httpd，不能当作真实设备 HTTP 端到端验证。b03 的结果仍限于本地对应样本和直接 CGI 对照。
