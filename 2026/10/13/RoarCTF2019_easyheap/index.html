RoarCTF 2019 easyheap

环境：Ubuntu 16.04 / libc-2.23（main_arena+88 = 0x3c4b78）
样本：pwn_patched + 对应 libc
保护：Full RELRO / Canary / NX / No PIE

菜单：1 add 2 delete 3 show 666 gift

要点：

  • uaf 漏洞

add/delete 单指针buf 0x602088，free 不清零

  • show 要 magic 0x602090 == 0xdeadbeefdeadbeef，show 完 close(1)/close(2) → 之后只能盲发
  • add函数：

add size ≤ 0x80，次数 0x602018 初值 16
并且，malloc地址只使用buf保留，属于单指针题目
buf地址： .bss:0000000000602088 buf

  • gift函数

选项666触发：

gift：calloc(0xa0,1)（申请 0xa0），堆上 chunk size 为 0xb0，随后 read(..., 0xa0)
或者删除 ptr 保留的 chunk
他也是单指针

题面观察（本题思路）

（1）单槽 + 无 edit → 不能常规 multi-chunk 玩；靠 gift 指针 + unlink 改指针

a.先使用buf指针，在fastbins中堆满不同size的chunk

b.然后再add一个位于较前位置的chunk,将他重新取回，再delete，用于覆盖buf保留的地址，为合并后前一段（gift 用户区 0xa0 / 整块 size 0xb0）中，让后续gift申请的chunk能覆盖buf的头

c.然后scanf一个超长输入，调用malloc的合并，合并一个可以放进unsortedbins的chunk

d.使用gift,从这个合并后的chunk中分一块（calloc 0xa0，堆上 size 0xb0）

e.然后部署unlink的相关配置，并覆盖buf指向的chunk头，用于伪造一个0x90chunk

f.free(buf)，触发unlink，把 gift 指针 0x602098 改成 0x602080（即 0x602098-0x18）

（2）show 被 random magic 锁死 → 先写 magic 再 leak

a.No PIE → username/info 落在固定 .bss

可使用 House of Spirit
通过 username（0x602060）、info（0x6020a0）写入，在 0x602070 / 0x6020b0 伪造 chunk 头（0x602078 处 size = 0x41）。
从而 free(gift 指向的假块)，将 0x602070 起 size 0x40 的块（到 0x6020b0）放入 fastbins

b.申请0x40的chunk,修改 magic ，去除magic锁，然后泄漏libc地址

（3）show 后无 stdout → 后半全 sendline/send，别 sendlineafter(b'>> ')

关键地址：

1. username / info 假块（House of Spirit）

（目的是 .bss 上能当块用。）

0x602070是伪造的chunk头
0x6020b0是伪造的第二个chunk头（用于过free检查）

2. 整理堆 + 超长 scanf 触发 consolidate

scanf("%d") 数字太长 → 内部 scratch 扩容 malloc → malloc_consolidate
fastbin 被合并进 unsorted，后面 unlink 的 prev_inuse / 尺寸才站得住。

不是“对齐输入”，是真改堆。长度要超过栈上 work buffer（2.23 约 1K 量级）。

3. unlink 劫持 gift 指针

如图：0x1431010：unlink的配置部分
0x14310b0：为伪造的chunk头的用户部分
（buf此时指向它，这样free（buf）时,就会当作0x90大小释放）

为了让这个0x90的chunk实现unlink
0x1431130:为下一个伪造的chunk头
0x1431160:为下下个伪造的chunk头

为什么要伪造这么多chunk头？
因为unlink是会检查前后的chunk是否为free状态

0x1431010和0x14310b0的伪造，是为了让unlink认为当前chunk前一个chunk为free,这样才能触发想起合并，修改ptr指针

0x1431130的伪造，是为了让free认为当前chunk是使用状态
（自身是否为使用状态，需要查看下一个chunk的inuse位）

0x1431160的伪造，是为了让unlink认为下一个chunk是使用状态
（原理同上，0x1431130的下一个chunk就是0x1431160）

为什么这次free,进的是0x40的fastbins呢？
因为，unlink合并后，ptr=ptr-0x18（0x602080）
然后我之前步骤1,部署的假块就在那个位置

所以，这次free,0x602070被当成chunk放入fastbins中了

unlink 后 0x602098 → 指向 0x602080 一带，后续能改主指针/magic。

4. 写主指针 + magic，leak libc

（1）magic 写成 0xdeadbeefdeadbeef → show 放行
（2）recv(6) 拿 unsorted 泄漏
（3）libc：

show 之后 stdout/stderr 没了，后面全盲发。

one 列表（本机 2.23）：

由于我show时申请了0x80,并且当时unsortedbins是有两个chunk,所以他将第一个chunk放进了smallbnins后，才进行的chunk分割

然后我delete后，heap布局如下：

我们可以发现，我之前在unlink时埋下的libc_base+0xa0处的伪造chunk,
再次帮助到我们了，smallbins处的chunk他覆盖了,unsortbins中的chunk

我可以从libc_base+0xa0处申请一个0x60大小的chunk,然后放入fastbins,
再用smallbins的chunk，修改他的fd指针，从而任意写
修改malloc_hook

为什么要先申请一个0x20？
因为，我当时一开始，布置fastbins,叠空间时，没算好。
导致这里直接申请0x60,分割剩下chunk的fd/bk会覆盖libc_base+0x130的chunk头+per_size，
那里保存着smallbins中chunk下一个的per_size信息，后续从里面申请空间，修改fastbins头时，
会用chunk分割,chunk分割会检查size和下一个per_size是否相等

那么此时就已经完成malloc_hook的修改，只差触发了
但是，如果直接用他的add,来触发malloc_hook,会发现add附近的栈环境中就没NULL；
所有用realloc_hook也没用，只能用一些别的来触发malloc_hook

1.scanf(“%d”)+大量写
2.free报错时，会用malloc保留缓存。
